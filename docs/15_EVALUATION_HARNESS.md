# 15 Parser evaluation harness (M-11)

Measures the deterministic rules parser (M-08) and the Gemini extraction parser
(M-10) against a manually curated golden dataset. The harness treats both parsers
as black boxes and compares their internal `parse.schema.ParseResult` with the
annotated expectations. It does **not** change parser behaviour, prompts,
normalisation, lexicon, segmentation or the public API.

## Package layout

```
backend/evaluation/
    __init__.py          # DATASET_VERSION
    schema.py            # EvaluationCase, Expected*, EvaluationResult, MetricSummary, EvaluationReport
    dataset/recipes.jsonl
    loader.py            # load_dataset + validation
    metrics.py           # evaluate_case + summarize
    report.py            # latest.json / latest.md renderers + comparison
    runner.py            # CLI: rules (offline) and gemini (explicit live)
    reports/latest.json  # generated
    reports/latest.md    # generated
```

## Dataset structure

`backend/evaluation/dataset/recipes.jsonl` is JSONL: one case per line.

| Field | Meaning |
|---|---|
| `id` | stable, unique case id |
| `text` | the original transcript (never normalised) |
| `script` | `bengali` \| `roman` \| `mixed` |
| `tags` | coverage tags (used only for reporting/slicing) |
| `expected_ingredients[].canonical` | M-07 canonical label |
| `expected_ingredients[].surface` | optional original surface form |
| `expected_ingredients[].quantity` | optional expected quantity (see below) |
| `expected_ingredients[].evidence` | exact phrase from the transcript that supports the fact |
| `expected_durations[]` | `{value, value_max?, unit, kind, evidence}` |
| `expected_clarifications[]` | `{kind, unit, evidence}` that must be raised |
| `expected_step_count` | optional expected number of steps |
| `negatives[]` | interpretations that must not occur |
| `notes` | optional human explanation |

`ExpectedQuantity.kind` is `exact | range | vague | taste | unresolved`, with
optional `qty`, `qty_max`, `unit`, `to_taste`.

Negative expectation kinds: `ingredient`, `ingredient_any`, `quantity_unit`,
`quantity_for_ingredient`, `clarification`.

### Coverage

21 curated cases cover: Bengali script, Roman Bengali, mixed script, multiple
ingredients in one segment, exact digits, spoken numbers, halves/decimals,
explicit ranges, traditional measures (মুঠো, চিমটি), vague quantities, taste
(স্বাদমতো), ambiguous চামচ and কাপ, resolved ছোট চামচ, multiple steps/connectors,
durations (minutes, hours), conditional + negation, unknown words, the মুইঠা
regression, and the full Chitol Macher Muitha narration.

## Ground-truth annotation rules

1. Expected facts are curated from the narration and the documented requirements
   (`docs/05_PARSER_SPEC.md`, the Chitol fixture, existing regression tests). They
   are **never** generated by asking Gemini or by copying parser output.
2. Every expected fact must cite an `evidence` phrase; the loader rejects a case
   whose evidence is not a literal substring of the transcript.
3. Use existing M-07 canonical labels. Do not invent ingredients, amounts,
   durations, servings or yield.
4. Preserve ambiguity: plain `চামচ`/`কাপ` must keep a clarification; a resolved
   compound (`ছোট চামচ`) must not be marked ambiguous.
5. `মুইঠা` is never annotated as a handful (`মুঠো`/`মুঠি`).
6. An ingredient without a clearly supported quantity is annotated with no
   `quantity` (ingredient recognition only), never with a guessed amount.
7. The dataset is parser-independent, so the same cases fairly evaluate both
   parsers.

## Metric definitions

| Metric | Definition |
|---|---|
| Ingredient TP/FP/FN | Per case, compare canonical **sets**: `tp = |expected ∩ actual|`, `fp = |actual \ expected|`, `fn = |expected \ actual|` |
| Ingredient P/R/F1 | Micro-averaged over all cases from the summed TP/FP/FN |
| Quantity accuracy | Over expected ingredients that carry a quantity: full match on kind, `qty`, `qty_max` (1e-6 tolerance) and unit |
| Quantity association accuracy | Share of those expected quantities where the ingredient got *any* quantity (scored separately from ingredient recognition) |
| Numeric quantity correct | Expected `exact`/`range` quantities whose numeric `qty` matches |
| Explicit range correct | Expected `range` quantities whose `qty` and `qty_max` match |
| Unit correct | Expected quantities whose unit matches |
| Vague preserved | Expected `vague` quantities that stay `vague` with no number |
| Taste preserved | Expected `taste` quantities that keep `to_taste=True` |
| Duration recall | Expected durations matched on value, `value_max` and unit |
| Duration value/unit correct | Component checks with their own denominators |
| Durations wrongly attached to ingredients | Actual ingredient quantities whose unit is `minute`/`hour`/`second` |
| Clarifications preserved | Expected clarifications actually raised |
| Ambiguity violations | Missing expected clarifications + forbidden clarifications present |
| Negative expectations | Each `negatives[]` check; violations are reported individually |
| Evidence grounding | Share of ingredient surfaces and quantity/duration `raw_phrase`s that are exact transcript substrings with valid spans |
| Unsupported assertions | Count and rate of grounded-fact failures (shown separately, never folded into F1) |

## Commands

Offline rules evaluation (no credentials, no network):

```bash
python -m backend.evaluation.runner --provider rules
```

Explicit live Gemini evaluation (requires `GEMINI_API_KEY`, `GEMINI_MODEL`, and
the confirmation flag; one request per case, no retries, no automatic rules
fallback):

```bash
python -m backend.evaluation.runner --provider gemini --confirm-live-api
```

Compare two existing reports side by side:

```bash
python -m backend.evaluation.runner --compare \
    backend/evaluation/reports/latest.json path/to/other.json
```

Reports are written to `backend/evaluation/reports/latest.json` (machine-readable)
and `latest.md` (readable, including per-case failures). Use `--reports-dir` and
`--dataset` to redirect output or run a different dataset.

## Report interpretation

- Read numerators/denominators, not only percentages.
- Failures list the expected fact, the observed value and the supporting
  transcript phrase, so the next parser fix is obvious.
- Ingredient precision/recall is set-based and is not the whole story; quantity
  association and unsupported assertions are reported separately.
- A case that could not be parsed by the live provider is counted as **not
  evaluated** and is never replaced by a rules result.
- A high score on this set means the documented cases are handled. It does **not**
  prove that every Bengali dialect, spelling variant or cooking style is
  supported.

## Known coverage limitations

- The dataset is small (21 cases) and curated; it is a regression baseline, not a
  representative sample of Bengali cooking language.
- Ingredient recognition is set-based; duplicate mentions of the same canonical
  are not penalised, and ingredient–quantity association is only scored for
  ingredients that carry an annotated quantity.
- The internal `ParseResult` has no servings/yield field, so "never infer
  servings" cannot be measured from it; it is documented rather than scored.
- The internal contract has no `pc` (piece) unit, so counts are annotated with
  `unit = null` (see case `c21`), which is why that case expects an unmeasured
  count.
- Live Gemini results depend on the configured model and are not run by pytest;
  provider failures are surfaced per case, not hidden.
